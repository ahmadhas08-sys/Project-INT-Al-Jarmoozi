# GitHub Projects Portfolio Observatory

## My interpretation of the brief

I understand this project as the development of a web application that provides a unified overview of multiple GitHub Projects. The main challenge is not only displaying project data, but handling the fact that different GitHub Projects may use different custom fields, statuses, priorities, and structures.

The application should retrieve authorized project data through the GitHub Projects API, map relevant fields into a common internal model, and provide useful views for individual users, projects, and higher-level portfolio monitoring. It should distinguish the current state of projects from historical changes by periodically collecting and storing project information.

The system should also identify useful conditions such as stale, overdue, soon-due, blocked, unassigned, or high-priority items when the available project data supports those conclusions. The result should be a monitoring application that helps users understand both the current state of their projects and how that state has changed over time.

## Why I am a good fit for this project

I am especially interested in computer networks, backend systems, and cloud technologies, and I would like my project to develop skills that are useful in that direction. This project interests me because it combines several areas that I want to understand more deeply: APIs, authentication, data storage, background processing, web applications, and the operation of an external cloud service such as GitHub.

I also like that the project has practical engineering problems rather than being only a user-interface application. Working with multiple GitHub Projects requires decisions about data normalization, synchronization, persistence, error handling, permissions, and API limitations. These are problems that I would like to learn how to design and solve properly.

## Proposed approach

I would begin by studying the GitHub Projects v2 GraphQL API and creating a small prototype that can authenticate with GitHub and retrieve the structure and items of one authorized GitHub Project. This would allow the API model, authentication requirements, pagination, permissions, and rate limits to be understood before building the larger application.

The next step would be to define a common internal data model for project items and configurable mappings between GitHub custom fields and common concepts such as status, priority, assignee, and due date. I would then extend the prototype to support multiple projects and persist collected project states so that the application can distinguish current information from historical changes.

On top of this data layer, I would implement the monitoring rules and dashboard views required by the brief. The collection process would run periodically rather than requiring the user to manually refresh every project. Error handling would cover authentication, permissions, unavailable or missing fields, API failures, pagination, and rate limits.

The implementation would be developed incrementally so that the GitHub integration, normalization, persistence, monitoring logic, and user interface can each be tested separately before being combined into the complete system.

## Initial plan

1. Study the GitHub Projects v2 GraphQL API, its authentication model, permissions, pagination, and rate limits.
2. Define the main users, use cases, project scope, common data model, and success criteria.
3. Build a proof of concept that retrieves and displays data from one authorized GitHub Project.
4. Design and implement configurable mappings from project-specific GitHub fields to the application's normalized model.
5. Add support for multiple projects and persistent historical snapshots or changes.
6. Implement monitoring rules for conditions such as stale, overdue, blocked, unassigned, and high-priority items where the available project data supports them.
7. Build the personal, project, and higher-level dashboard views and a change feed based on the collected data.
8. Add scheduled data collection and robust handling of authentication, permission, API, and rate-limit failures.
9. Test the normalization, monitoring rules, persistence, and GitHub API boundary and evaluate the completed system with representative project configurations.
10. Document the architecture, important design decisions, limitations, security considerations, and deployment process.
